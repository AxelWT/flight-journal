# 《深入理解 AI Agent》思维链导图

> 源笔记：[ai-agents-in-depth.md](./ai-agents-in-depth.md)
> 组织方式：每章从顶层问题出发，逐层拆解为子问题，问题体现拆解逻辑，答案从原文提炼。

---

## 全书总览

**Q：这本书的核心论点是什么？**
→ 模型智力只是基础，Agent 的能力上限由上下文质量、记忆体系和工具设计这三项系统工程决定；模型固定时，提升 Agent 的主要手段是重新定义观察空间（上下文）与动作空间（工具）。

**Q：各章之间是什么逻辑关系？**
→ 第 1 章定义 Agent 是什么（Agent = Model + Harness）；第 2 章解决"喂什么"（上下文工程）；第 3 章解决"记什么"（用户记忆与知识库）；第 4 章解决"用什么"（工具设计）；三者共同构成 Harness 工程的主体。

---

## 第 1 章　AI Agent 入门

### Q1：现代 Agent 由什么构成？

→ Agent = LLM + 上下文 + 工具。观察通道（上下文）和动作接口（工具）构成 Agent 与环境的边界；Harness 负责在两者之间做翻译和保障。

#### Q1.1：LLM 每次调用的上下文由哪几部分组成？

→ 五部分：系统提示词、工具定义、用户消息、模型回复、工具执行结果。

**Q：这五部分的结构性区别是什么？**
→ 前两项（系统提示词 + 工具定义）是静态前缀，在整个对话中保持不变；后三项是随交互不断增长的动态消息历史。

**Q：模型回复最多包含哪三个部分？**
→ 思考过程（内部思维链）、文本内容（给用户的回复）、工具调用请求（采取行动的方式）；三者不一定同时出现——调工具时通常只有 reasoning + tool_calls，给最终回答时只有 reasoning + content。

**Q：如何验证每个组件是否不可或缺？**
→ 消融实验（Ablation Study）：逐一去掉某个组件看系统是否还正常，从而判断每个组件的贡献。

#### Q1.2：Agent 执行任务的核心模式是什么？

→ ReAct 循环（Reasoning + Acting）：想 → 做 → 看 → 想 → 做 → 看，不断重复直到任务完成。实际包含三个环节——思考当前该做什么、调用工具行动、观察工具结果并继续思考。

#### Q1.3：模型之外还需要什么工程？

→ Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正。以 Claude Code 为例，绝大部分代码是约束、验证与纠正，而非工具本身——工具只是一小部分，围绕工具构建的保障机制才是核心。

**Q：Harness 具体包含哪些保障机制？**
→ 流程状态管理（追踪执行到哪一步）、多层上下文压缩、权限分类、熔断器（错误连续发生时自动停止重试）、错误恢复（捕获异常、回滚、重试或交还人类）。

**Q：Agent 的伪代码主循环怎么写？**
→ 观察 → 循环{构建上下文 → 模型生成动作 → 无动作则退出 → 约束过滤 → 应用到环境 → 验证失败则纠正 → 追加到轨迹}。

#### Q1.4：模型越来越自主，Harness 工程为什么反而更重要？

→ 决策越自主，决策失误的影响就越大，越需要 Harness 兜底保障可靠性与安全性；未来 Harness 可能不再负责编排，但给模型决策兜底和引入人工审核不可缺少。

### Q2：如何构建有效的 Agent 系统？

#### Q2.1：构建的核心原则是什么？

→ 保持简单、保持透明、设计好工具接口（ACI，Agent-Computer-Interface）——从 Agent 视角设计接口，命名和参数直观，容易误用的地方从设计上让错误无法发生。

#### Q2.2：系统该如何编排？

→ 两条路线：工作流（预定义代码路径，确定性执行，LLM 只在节点内负责理解生成）与自主 Agent（执行路径由 Agent 根据环境反馈实时决定）。

**Q：工作流的局限是什么？**
→ 缺乏变通性——出现预设流程未覆盖的情况（用户临时改签、航班取消）时只能走异常分支或交还人类。

**Q：两者如何选择？**
→ 混合使用：关键的、有严格合规要求的流程用工作流确保可靠性，需要灵活决策的部分切换到自主模式（如 n8n 可在同一系统中混用两种节点）。

**Q：航班订票客服该选哪种模式？**
→ 混合模式：先用 Agent 节点思考订票注意事项并向用户提问决策，再用工作流的确定性流程执行预订。

#### Q2.3：如何保障 Agent 行为安全可控？

→ 分层护栏（Guardrails），按被绕过的难度排三层：上下文层（管模型能看到什么，进入前拦截）、执行层（管模型能做什么，动作生效前验证）、数据层（管世界最终被改成什么样，由经过人类审查的稳定机制强制执行）。

**Q：为什么上下文层护栏给不出保证？**
→ 处在同一个上下文里的 Agent 很难判断自己是否已被注入——这是结构性上限，所以必须有执行层和数据层。

**Q：执行层护栏的核心机制是什么？**
→ 工具风险评级：按可逆性、权限等级、财务影响为每个工具标注风险等级，高风险操作需额外审查或人工确认。

**Q：参数不同风险不同怎么办（如 delete_file 删普通文件 vs 系统文件）？**
→ 按本次具体调用的参数动态定风险；规则未覆盖的参数组合默认给高风险以保证安全。

**Q：人工干预（Human in the loop）的价值是什么？**
→ 让 Agent 在不损害用户体验的前提下提升实际性能，部署早期尤为重要——识别失败模式、发现边缘情况、建立评估周期。

**Q：用户不在线或响应很慢时 Agent 怎么办？**
→ 高风险默认暂停，低风险降级继续，所有状态存好并最好能回滚。

### Q3：贯穿全书的设计模式有哪些？

**Q：产出与评判如何分离？**
→ 提议者-审核者（Proposer-Reviewer）：两个不共享上下文的角色分别承担，评判方看产物本身（渲染结果、测试输出、调用参数）而非产出方的推理过程；成立前提是自审不可靠。

**Q：信息太多如何喂？**
→ 渐进式披露（Progressive Disclosure）：先给可检索的目录，再按需加载细节。

**Q：状态如何演进才可信赖？**
→ 只增不改（Append-only）：换来可缓存、可重放、可审计。

**Q：如何验证一次修改是安全的？**
→ 边界集 + 保留集：同时在"应当改变的那批样本"和"不应当影响的那批样本"上验证。

**Q：修改如何做到可归因？**
→ 最小 diff + 可回滚：每次修改尽量小、带来源、可单独回滚，出了问题能定位到具体哪一次改动。

## 第 2 章　上下文工程

### Q1：为什么说上下文决定 Agent 的能力上限？

→ 一个中等能力的模型配上精心组织的上下文，往往胜过顶级模型在信息匮乏下的盲目摸索；以 Coding Agent 为例，缺了代码信息、流程规范、环境信息这三类最低信息需求，Agent 写出的代码可能语法正确但架构冲突、直推主分支、本地能跑测试环境即崩。

### Q2：Agent 调用 LLM 的 API 上下文长什么样？

→ 核心逻辑只有一个 while 循环和一个判断：模型返回 tool_calls 就执行工具并把结果追加进 messages 继续循环，没有就输出结果退出——整个过程中 messages 列表只增不减。

### Q3：如何设计对 KV Cache 友好的上下文？

#### Q3.1：KV Cache 的工作原理是什么？

→ 模型每生成一个 token 都要回看前文所有 token 的中间计算结果；KV Cache 把前文的中间结果缓存下来，下一轮只算新增部分。前提是复用的上下文 token 前缀保持不变——从首个不同的 token 起，缓存需要重算。

#### Q3.2：由此得出哪三条核心结论？

→ ① 系统提示词和工具定义一旦确定就不要改（哪怕一个空格都可能破坏缓存）；② 动态信息永远追加到末尾，不修改已有前缀；③ 使用标准 API 格式，不要自行拼接 "USER: ... ASSISTANT: ..." 消息。

#### Q3.3：常见的错误上下文管理模式有哪些？

→ 五种反模式：

- **动态系统提示词**（系统提示词加时间戳）：应把时间信息作为用户消息追加到末尾，或需要时通过工具获取。
- **动态用户配置**（每次请求更新余额等）：破坏缓存，应交给专门的状态管理机制。
- **工具定义动态排序**：改变顺序让缓存从首个变动的工具起全部失效；实验表明保持固定顺序对工具选择能力几乎没有影响。
- **滑动窗口**（只保留最近几条消息）：既破坏前缀一致性，又丢失关键的工具结果——实验中使用滑动窗口的 Agent 常陷入循环，反复执行相同调用。
- **文本格式化**（转为纯文本流）：关键不在缓存，而在于偏离训练时的角色结构格式，导致重复执行、忽略结果、格式解析错误等各种问题。

#### Q3.4：KV Cache 和 Prompt Cache 有什么区别？

→ KV Cache 是模型内部机制（加速单次请求内的 token 生成），Prompt Cache 是推理引擎优化（在多次 API 请求之间复用相同前缀的计算结果）；两者都利用前缀不变性，但作用层级不同。

#### Q3.5：缓存如何反过来约束架构？

→ 当 Prompt Cache 经济效益足够显著时，缓存一致性会反过来主导系统结构：动态元素都往后放、子 Agent 与父 Agent 字节级对齐以命中缓存、工具结果替换字符串首次出现即持久化。

**Q：滑动窗口丢信息与全量保留爆上下文如何两全？**
→ 口诀：前面别乱改，后面只追加，旧内容别丢，放到外面能查。

**Q：ReAct 循环的 KV Cache 读取量为何近似二次方增长？**
→ 上下文只增不减，第 n 轮要读取前 n-1 条消息的缓存，累计为 O(n²)；解决思路是按需携带关键信息、历史过多时压缩（注意压缩后缓存重建）、用子 Agent 隔离。

### Q4：系统提示词该怎么写？

→ 六个优化方向：

- **语气与风格**：大写强调（Never do X）能引起模型注意，但过度使用会稀释效果，保留给真正关键的约束。
- **结构化提示**：用 markdown 标题、XML 标签表达层次与精确语义——模型对结构化输入显著敏感。
- **流程驱动优于规则堆砌**：像优秀的新员工培训手册，提供清晰的 SOP（先干什么、再干什么、怎么收尾）。
- **业务规则细化**：让 Agent 在明确框架内发挥能力。
- **Few-shot 示例**：当期望输出难以用规则精确描述时，直接给出高质量的输入-输出示例。
- **防注入**：来源标记（包裹并标注不可信来源）、指令与数据分离（严格用角色体系传信息）、输入清洗（过滤可疑模式）。

**Q：多人维护系统提示词如何防止"熵增"？**
→ 审核，不让人人乱改，派专人维护。

### Q5：提示词越写越长怎么办？

→ Agent Skills 的渐进式披露机制：按需加载，而非一次性塞满（既浪费 token，又稀释注意力）。

**Q：Skill 在上下文中的位置如何安排？**
→ 标准只规定加载时序而非消息角色：目录必须先于正文可发现，正文在被选中后按需加载。Claude Code 的实现是目录作为运行时上下文消息提供，完整指令在被调用位置作为 user message 注入。

**Q：模型不知道自己不知道，无法触发 Skill 加载怎么办？**
→ 模型可以不知道自己不知道，但系统必须在结构上安排它在关键节点看一眼（如小模型/工具做 skill 检索匹配）。

**Q：加载了 Skill 就等于持续遵从吗？**
→ 不——加载 Skill 不等于持续遵从，长轨迹中义务会一条条静默漏掉。

### Q6：如何让 Agent 感知自己的运行时状态？

→ Agent 状态栏：把任务进度、环境变化、工具调用计数等动态信息整理成结构化摘要，作为 user 角色消息插入上下文末尾（而非修改开头的 system 消息）。

**Q：状态栏包含哪些内容？**
→ 任务规划（TODO 列表放轨迹末尾）、事件侧信道信息（时间、位置、时间间隔）、环境观察摘要（系统时间、工作目录、异常提醒如"该工具已被重复调用 N 次"）。

**Q：状态更新有两种实现，如何取舍？**
→ 实现一"每轮替换"：移除旧状态追加新状态，保证只有一份最新状态，代价是旧位置之后的缓存失效；实现二"持久追加"：缓存友好，代价是陈旧状态积累。状态小、两次更新间消息多、会话长度受控时选持久追加；状态大、更新频繁、轨迹很长时选每轮替换。

**Q：状态栏维护要注意什么？**
→ ① 尽量用代码维护，用 LLM 也要逐条抽取再由代码汇总，绝不让 LLM 一次性批量统计；② 谨慎删除原始上下文。

**Q：状态栏本身出错（计数器 bug）怎么办？**
→ 计数、阈值这类交给代码算，别交给模型"感觉"，且计算组件必须写测试。

### Q7：上下文膨胀了怎么办？

#### Q7.1：为什么注意力机制需要外部辅助？

→ 注意力擅长在已有内容里"查找"，不擅长在一次前向传播里"归纳统计"——上下文学习本质上是检索而非推理。状态栏（代码确定性维护）和压缩（LLM 蒸馏）是同一枚硬币的两面，都在给这台"只有一半"的检索引擎补上缺失的"提炼"。

**Q：状态栏也常由 LLM 生成，这矛盾吗？**
→ 不矛盾，关键在量级：小范围、近期、目标明确的归纳准确率可接受；信息量膨胀到整个长对话历史时，注意力出现"归纳瓶颈"——找得到相关信息，但难以综合成准确的全局结论。

**Q：三者如何对比？**
→ 状态栏（LLM 生成）：面对最近几百~几千 token，提炼"当前做到哪了"，出错成本低；压缩（LLM 蒸馏）：面对整个对话历史上万 token，提炼"过去 50 轮所有关键决策"，出错成本高、易丢细节；纯注意力：无提炼全靠检索，长程召回差。

#### Q7.2：压缩如何与 KV Cache 共存？

→ 压缩发生在两次 API 调用之间，由框架对消息列表预处理：静态前缀永远不动；压缩对象是对话历史中的 tool results，替换位置之后的缓存失效、之前仍有效。这是有意识的权衡——不压缩则上下文超窗任务直接失败。频次上最好接近阈值时批量压缩，而非每轮都压。

#### Q7.3：压缩策略有哪几档？

→ 五档递进：① 无压缩；② 非任务感知压缩（缺语义理解，无法区分相关性）；③ 上下文感知压缩（压缩提示中带 query 和 context，效果好）；④ 带引用的上下文感知（语义压缩有损 + 源链接无损索引，可随时回溯）；⑤ 自适应窗口化（小于 80% 保留原文，超出批量压缩）。生产系统通常组合为分层压缩机制。

**Q：128K 字符压到 2000 字符的极端压缩如何避免不可逆损失？**
→ 核心思路：不要把"压缩"做成"删除"，要做成"索引 + 可回查"。

#### Q7.4：有没有比压缩更釜底抽薪的方案？

→ 隔离优于压缩：子 Agent 上下文隔离——把"大范围搜索"这类产生海量中间内容的任务委派给子 Agent，它在自己的上下文中完成探索，只把几百 token 的结论性摘要回传主上下文。

**Q：思考内容（reasoning）该留该扔？**
→ 行业定位已从"可丢弃的 token 消耗品"（DeepSeek R1 剥离全部历史思考）转向"必须维护的运行时状态"（V4 强制回传全部 reasoning_content）——思考链是 Agent 的草稿纸，写着目标、假设、排除项和下一步。工程上不是"全留"或"全扔"二选一，而是近处保原文、远处压状态。

## 第 3 章　用户记忆和知识库

### Q1：如何理解持久化记忆体系的两个尺度？

→ 用户记忆是针对单个用户的个性化记忆（让 Agent 成为"懂你的助手"，代表框架 Mem0）；知识库是面向所有用户共享的集体知识（让 Agent 成为"领域专家"，代表技术 RAG/embedding）。

### Q2：用户记忆系统如何设计？

#### Q2.1：记忆分几层？

→ 两层：轨迹（单次会话的完整原始记录，按时间追加且不修改——流水账）和长期记忆（跨会话提炼的稳定信息，反复改写合并淘汰——档案）。

#### Q2.2：记忆用什么格式存储？

→ 四种：Simple Notes（最小不可分事实，开销低但丢失关联）、Enhanced Notes（带完整上下文的段落，代价是重复与重写复杂）、Json Cards（类别→子类别→键值对三层嵌套）、Advanced Json Cards（加入来源叙事、主体身份、关系、时间戳——同一条信息在不同场景含义完全不同）。实践标准：关键且少量用 Advanced JSON Cards，大量非关键用 Simple Notes，多数系统混合使用。

#### Q2.3：认知科学如何映射到 Agent 记忆？

→ 工作记忆 = 上下文窗口（含轨迹和从长期记忆激活加载的信息）；情景记忆 = 具体事件（"用户订了下周五去东京的 ANA 航班"）；语义记忆 = 抽象出的稳定知识（"用户是素食者"）；程序记忆 = 行为模式与流程（"先搜直飞 → 确认座位偏好 → 用常旅客号 → 订餐"）。

#### Q2.4：记忆如何压缩与整理？

→ 三层：重要性评分筛选（访问频率、时间衰减、情感强度、信息独特性）→ 聚类（相似记忆分组生成代表性摘要）→ 抽象与泛化（从情景记忆提炼为语义或程序记忆）。

#### Q2.5：工程上如何既保留原始证据又得到可查询状态？

→ 会话结束后先把事实追加到只增日志，再定期从完整日志重建带类型的状态（append-only 原始层 + 派生聚合层 + 提供给模型的记忆工具）。

**Q：用户在不同会话给出矛盾信息（两个住址）怎么办？**
→ 两条记录都保留并标上时间；回答时先判断用户问题（或问用户细节）再取对应时间的记录。

**Q：Mem0 和 Memobase 的思路差异？**
→ Mem0：一次 LLM 调用抽取事实、只做 ADD，查询时融合语义相似度和时间信息排序；Memobase：用户画像（可配置槽位存稳定属性）+ 事件记忆（时间线），采用缓冲批处理摊薄 LLM 调用成本、查询侧只读整理好的画像保证低延迟。

### Q3：RAG 的基础管道如何搭建？

**Q：核心流程是什么？**
→ 文档切块 → embedding 向量化 → 存入向量数据库 → 检索时对查询词 embedding → 相似度检索取回分块 → 注入上下文 → LLM 生成。

**Q：如何提高检索精度？**
→ 三板斧：混合检索（向量语义 + BM25 关键词，取长补短）、重排序（向量库快速召回 Top-50/100，交叉编码模型精排取 Top-3/5）、上下文压缩/精炼（小模型提取关键句子再进 Prompt）。

#### Q3.1：文档如何分块？

→ 四种策略：固定大小切分（简单但截断关联信息）、递归/结构感知切分（按章节段落句子递归，生产默认选择）、语义切分（在嵌入相似度骤降的"语义断崖"处切分，质量高但需额外计算）。块大小与重叠量是典型权衡：块太小语义模糊（"收入增长 3%"——哪家公司？），块太大嵌入稀释、精度下降；常见起点 256-1024 token、重叠 10%-20%。

#### Q3.2：稠密嵌入与稀疏嵌入分别解决什么问题？

→ 稠密嵌入（Word2Vec → GloVe → BERT → Sentence-BERT → BGE-M3）：深度学习把文本映射到向量空间，语义相近则向量距离近，用余弦相似度检索——但可能漏掉关键词。稀疏嵌入（TF-IDF → BM25）：极高维向量、绝大多数维度为零，基于词袋模型做精确关键词匹配——但不理解语义（"猫追狗"和"狗追猫"完全相同）。生产中 ANN 算法（近似最近邻，类跳表 O(log N)）支撑百万级文档的快速查找。

#### Q3.3：检索质量用什么指标衡量？

→ recall@k（前 k 个里有没有相关文档，只看"有没有"）；MRR（第一个相关文档排第几，只看"第一个"）；nDCG（整体排序质量，越多相关文档排得越靠前越好，靠后的折扣越大）。

### Q4：扁平文本检索什么时候不够用？

**Q：判断标准是什么？**
→ 查询主要是"找到包含某信息的文档片段"（如"退款政策是什么"）时混合检索就够；查询需要跨文档综合（"SSE 和 AVX 指令集在架构上有什么区别"）或多层次导航（"从整体架构到具体指令逐步深入"）时，结构化索引才值得投入——代价是索引构建和查询都要更多 LLM 调用。

**Q：扁平检索的两个典型失效案例是什么？**

- **黑猫白猫计数**：100 个案例块（90 黑 10 白），top-k=20 只能看到不完整样本，模型得出错误比例——预先生成统计摘要（"共 100 只：90% 黑、10% 白"）并索引，一次检索即得准确答案。
- **Xfinity 优惠资格边界**：几百条个案工单没有一条写资格范围本身；最近邻偏置（"护士"最接近"医生"的工单）、边界语义缺失（"仅限……其他一律不适用"不存在于任何单条）、完整性信号缺失（模型不知道自己没看全）。解法是离线通读工单库提炼规则卡。

→ 共同结论：把原始案例不加处理地放进知识库远远不够，必须在索引阶段主动提炼、抽象和结构化。

### Q5：结构化索引有哪几条路线？

#### Q5.1：树状层次索引（RAPTOR）适合什么？

→ 自下而上递归抽象：全局摘要 → 聚类摘要 → 具体文本块。查询"SSE 指令集"时从"SIMD 指令集"宏观概念沿树向下钻取到叶子细节——适合"从概念逐步钻进细节"的查询。

#### Q5.2：实体关系图索引（GraphRAG）适合什么？

→ 文档知识建模为实体-关系三元组（主语-关系-宾语，如（北京，是首都，中国））构成的知识图谱。查询"SSE"时定位实体、遍历关系边到"XMM 寄存器"、"浮点运算"——适合"A 和 B 之间是什么关系"的关系性查询。

**Q：知识图谱的固有局限是什么？**
→ 三元组化导致语义降级（"如果下周还下雨就取消海边计划改去博物馆"的条件逻辑和时间依赖全部丢失），且提取准确性依赖 LLM、错误提取导致知识污染。推荐分层互补：完整自然语言保存核心信息 + 结构化元数据做索引检索。

**Q：RAPTOR 和 GraphRAG 如何选？**
→ 前者管抽象层次（跨层穿梭），后者管关系网格（图上漫游）；生产场景组合使用通常比单选效果好。

#### Q5.3：文件系统范式（OpenViking）是什么思路？

→ 把所有上下文（记忆、资源、技能）映射为虚拟文件系统的目录和文件（viking://resources/、user/memories/、agent/skills/），每个条目有唯一 URI；核心是 L0/L1/L2 三层按需加载——L0 摘要约 100 tokens 判断相关性、L1 概览约 2000 tokens 支撑规划决策、L2 全文仅在深入时加载，大部分查询到 L1 即完成。选 Markdown 纯文本而非专用数据库，是为了用户可直接阅读编辑、可 Git 版本控制回滚。

**Q：文件系统范式相比向量数据库 RAG 何时更有优势？**
→ 需要人机共同维护、需要追溯和回滚、Agent 要自己探索而不是一次召回的场景。

### Q6：知识应该如何更新？

→ 双路径：事件触发的增量更新（把知识库当代码库，每次知识变更当一个 Pull Request）+ 周期触发的全量整理（去重去旧合并、回到原始数据核查、冲突解决与场景限定）。

**Q：Reviewer 与 Proposer 同模型且只看上游挑选的片段，会合入什么错误？**
→ 三方面改进：Reviewer 换不同家族的模型（模型独立性）；Reviewer 能自主检索完整知识库和原始证据（证据覆盖）；强制分工——Proposer 只写工作分支，Reviewer 只读证据提交结论，只有合并流程能更新主分支（工具权限）。

### Q7：Agentic RAG 与传统 RAG 的区别是什么？

→ 把 RAG 检索做成一个工具，由模型决策是否检索、检索到什么程度；模型可以分解问题进行多步检索。注意 RAG 的安全边界——防知识库投毒。

**Q：如何解决分块丢失上下文的问题？**
→ 上下文感知检索（Contextual Retrieval）：向量化索引前先用 LLM 为每个文本块生成包含核心上下文的前缀摘要，前缀与原文块拼接后再索引。

**Q：主动服务如何落地？**
→ 双层记忆架构：Advanced JSON Cards 把少量关键事实结构化常驻上下文（全局概览），上下文感知检索按需从海量原始对话取回细节（精确细节）——只靠常驻会丢细节，只靠检索会缺全局视野，两者结合才能主动服务。

## 第 4 章　工具

### Q1：工具分哪几类？

→ 五类：感知工具（获取信息：web_search、knowledge_base_search）、执行工具（改变世界：shell_exec、write_file）、协作工具（与其他 Agent/人协作：spawn_subagent、send_message）、用户沟通工具（向用户传递信息：reply_to_user、send_card）、事件触发工具（外部世界驱动 Agent：set_timer、monitor_shell）。

### Q2：一项能力该用什么形式表达？

**Q：专用工具、通用执行器、Skill 如何选？**
→ 默认取向：通用工具优于专用工具，除非有明确的安全、权限或性能理由。具体看四点：① 安全与权限（需精细授权、审计留痕、不可逆风险 → 专用工具封装）；② 参数复杂度（嵌套对象、多字段联合校验 → 专用 schema 引导，简单参数走 CLI 即可）；③ 变更频率（频繁变化 → Skill，改文本远比改代码部署轻；稳定底层 → 专用工具）；④ 模型能力（强模型用 Skill + 通用执行器表达更多能力，弱模型需要结构化 schema 引导）。

**Q：通用执行器还有什么常被忽视的好处？**
→ 让模型用代码编排工具调用——用代码串联多个工具，而不是一次调一个、把每个中间结果都搬进上下文。

### Q3：工具描述该怎么写？

→ 核心是让 LLM 知道"什么时候用"，而不只是"能做什么"："当需要获取实时信息或查找未知事实时使用" 优于 "搜索相关内容"。要点：边界条件（做不到什么、不接受什么）往往比能力描述更重要；参数描述用具体例子代替抽象规范；返回值结构写清楚（"返回 JSON 数组，含 title/url/snippet"）；为每个工具附 1-5 个真实调用示例。

**Q：Agent 频繁选错工具时先查什么？**
→ 优先检查工具描述而不是怀疑模型能力——大多数选择错误的根因是描述不准确（边界不清、缺少反例、参数含义模糊）。

**Q：参数传递的保真性指什么？**
→ 模型感知到的世界与工具操作的世界之间不能存在系统性偏差——不得在模型不知情的情况下静默修改输入或输出（如把弯引号偷换成直引号，会让模型读取验证时陷入困惑）。

### Q4：工具生态如何构建？

**Q：MCP 是什么？**
→ 客户端-服务器架构的标准化协议：MCP 服务器暴露一组工具，客户端（Agent 框架/IDE）通过标准协议通信；JSON Schema 定义参数；传输层本地用 stdio、远程用 Streamable HTTP；资源与工具分离。

**Q：Skill 如何分发？**
→ 不需要协议——一个 Skill 就是一个装着 SKILL.md 的文件夹，分发机制是注册表（registry）而非协议。

**Q：接入第三方能力的共同风险是什么？**
→ 把一段不受自己控制的文本注入 Agent 上下文，往往还把凭证交到别人手里。对策：接入前审查工具描述、锁定服务器版本、为每个服务器配最小权限凭证。

### Q5：工具太多怎么办？

→ 三层解法，一层比一层"按需"：

- **层次化组织与按需加载**：按信息源性质分类（搜索/读取/解析/查询），不把全部定义一次性塞进上下文；检索式预筛选按语义相似度先筛候选——局限是按初始查询一次性匹配，无法预见多步骤跨领域的工具链需求。
- **主动工具发现**：Agent 执行中意识到能力缺口时主动用自然语言声明需求，系统动态匹配注入；工程上等价于保留少数基础工具 + 一个"工具搜索工具"。KV Cache 友好的做法：新工具 schema 追加到上下文末尾，静态前缀保持稳定，schema 固定在轨迹原位置继续命中缓存。
- **Skills**：不把工具当正式定义注册检索注入，而当成可随手翻阅的参考资料。

**Q：还有别的思路吗？**
→ 参考人类专家：先分专业领域，再按岗位给权限，最后小范围试错。

### Q6：感知工具要注意什么？

→ 搜索类返回要分页：默认只返回前若干条并注明总数和翻页方式，由 Agent 自主决定是否继续，不一次性倾倒；读取类要有 offset/limit 和截断策略，截断时明确标示省略了多少、如何读剩余。多模态感知有三条路径：模型原生多模态、自动提取为文本再处理、把多模态模型封装为工具。

### Q7：执行工具如何平衡能力与安全？

→ 八项机制：输入验证（防 `../` 越界）、权限控制（工作目录限制、命令黑名单、API 配额）、提议者-审核者（不同供应商模型独立审查，两个模型系统提示词一致但关注点差异——提议强调行动导向，审批强调风险控制）、Sidecar 机制（与主思考并行的轻量级安全校验；也用于旁路构造上下文——筛选记忆、摘要长输出，主模型需要时已就绪）、可验证则自动验证、长输出截断与持久化（头尾入上下文，全文存临时文件）、沙盒隔离、可观测性（日志、审计追踪、性能指标、告警）与幂等性/取消语义。

#### Q7.1：沙盒隔离的层级如何递增？

→ ① 进程级（Claude Code/Codex 默认本地执行——但注意实际权限取决于宿主的沙盒与审批策略，如 Codex 的 workspace-write、Claude Code 的只读起始权限）；② 容器（独立文件系统和网络栈，但共享内核，内核漏洞可能逃逸）；③ microVM/虚拟机（Firecracker，独立内核的硬件级隔离，运行完全不可信代码的最强层级）。常见误区：venv 不是沙盒——只隔离包依赖，对文件系统、网络、进程没有任何安全约束。容器和 microVM 还应设 CPU/内存/磁盘/网络上限。

#### Q7.2：幂等性与取消语义如何设计？

→ 核心问题：调用被取消或超时后，副作用到底发生了没有（转账超时可能已转出，盲目重试就重复转账）。幂等性让"执行一次"和"执行多次"对外部世界影响相同，可安全重试：手段一是操作携带唯一标识由服务端去重，手段二是先查询后变更。不可幂等的操作（发邮件、对外转账）用"预检-确认"两段式：先用不同模型家族 + 专用安全提示词做校验，再真正执行；执行失败不盲目重试，把详细错误返回主模型重新规划。

### Q8：协作工具如何设计？

→ 三组原语：启动与取消（spawn_subagent / cancel_subagent——任务失去意义时及时终止避免浪费 token）、消息传递（双向 send_message）、发现（list_agents 列出可用 Agent 及职责与状态——与 MCP 的 tools/list 同一思路）。其上承载四种形态：同步调用、异步调用（任务 ID + 事件通知）、流式协作、多轮交互。再叠加人工介入、超时和降级策略、反馈循环（可归纳的判断进知识库或 Skill，隐式偏好形成后训练数据）。
