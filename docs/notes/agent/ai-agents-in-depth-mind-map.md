# 《深入理解 AI Agent》思维链导图

> 源笔记：[ai-agents-in-depth.md](./ai-agents-in-depth.md)（第 1～4 章）、[ai-agents-in-depth-II.md](./ai-agents-in-depth-II.md)（第 5～10 章）
> 组织方式：每章从顶层问题出发，逐层拆解为子问题，问题体现拆解逻辑，答案从原文提炼。

---

## 全书总览

**Q：这本书的核心论点是什么？**
→ 模型智力只是基础，Agent 的能力上限由上下文质量、记忆体系和工具设计这三项系统工程决定；模型固定时，提升 Agent 的主要手段是重新定义观察空间（上下文）与动作空间（工具）。

**Q：各章之间是什么逻辑关系？**
→ 第 1 章定义 Agent 是什么（Agent = Model + Harness）；第 2 章解决"喂什么"（上下文工程）；第 3 章解决"记什么"（用户记忆与知识库）；第 4 章解决"用什么"（工具设计）；三者共同构成 Harness 工程的主体。

## 第 1 章　AI Agent 入门

### Q1：现代 Agent 由什么构成？

→ Agent = LLM + 上下文 + 工具。观察通道（上下文）和动作接口（工具）构成 Agent 与环境的边界；Harness 负责在两者之间做翻译和保障。

#### Q1.1：LLM 每次调用的上下文由哪几部分组成？

→ 五部分：系统提示词、工具定义、用户消息、模型回复、工具执行结果。

**Q：这五部分的结构性区别是什么？**
→ 前两项（系统提示词 + 工具定义）是静态前缀，在整个对话中保持不变；后三项是随交互不断增长的动态消息历史。

**Q：模型回复最多包含哪三个部分？**
→ 思考过程（内部思维链）、文本内容（给用户的回复）、工具调用请求（采取行动的方式）；三者不一定同时出现——调工具时通常只有 reasoning + tool_calls，给最终回答时只有 reasoning + content。

**Q：如何验证每个组件是否不可或缺？**
→ 消融实验（Ablation Study）：逐一去掉某个组件看系统是否还正常，从而判断每个组件的贡献。

#### Q1.2：Agent 执行任务的核心模式是什么？

→ ReAct 循环（Reasoning + Acting）：想 → 做 → 看 → 想 → 做 → 看，不断重复直到任务完成。实际包含三个环节——思考当前该做什么、调用工具行动、观察工具结果并继续思考。

#### Q1.3：模型之外还需要什么工程？

→ Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正。以 Claude Code 为例，绝大部分代码是约束、验证与纠正，而非工具本身——工具只是一小部分，围绕工具构建的保障机制才是核心。

**Q：Harness 具体包含哪些保障机制？**
→ 流程状态管理（追踪执行到哪一步）、多层上下文压缩、权限分类、熔断器（错误连续发生时自动停止重试）、错误恢复（捕获异常、回滚、重试或交还人类）。

**Q：Agent 的伪代码主循环怎么写？**
→ 观察 → 循环{构建上下文 → 模型生成动作 → 无动作则退出 → 约束过滤 → 应用到环境 → 验证失败则纠正 → 追加到轨迹}。

#### Q1.4：模型越来越自主，Harness 工程为什么反而更重要？

→ 决策越自主，决策失误的影响就越大，越需要 Harness 兜底保障可靠性与安全性；未来 Harness 可能不再负责编排，但给模型决策兜底和引入人工审核不可缺少。

### Q2：如何构建有效的 Agent 系统？

#### Q2.1：构建的核心原则是什么？

→ 保持简单、保持透明、设计好工具接口（ACI，Agent-Computer-Interface）——从 Agent 视角设计接口，命名和参数直观，容易误用的地方从设计上让错误无法发生。

#### Q2.2：系统该如何编排？

→ 两条路线：工作流（预定义代码路径，确定性执行，LLM 只在节点内负责理解生成）与自主 Agent（执行路径由 Agent 根据环境反馈实时决定）。

**Q：工作流的局限是什么？**
→ 缺乏变通性——出现预设流程未覆盖的情况（用户临时改签、航班取消）时只能走异常分支或交还人类。

**Q：两者如何选择？**
→ 混合使用：关键的、有严格合规要求的流程用工作流确保可靠性，需要灵活决策的部分切换到自主模式（如 n8n 可在同一系统中混用两种节点）。

**Q：航班订票客服该选哪种模式？**
→ 混合模式：先用 Agent 节点思考订票注意事项并向用户提问决策，再用工作流的确定性流程执行预订。

#### Q2.3：如何保障 Agent 行为安全可控？

→ 分层护栏（Guardrails），按被绕过的难度排三层：上下文层（管模型能看到什么，进入前拦截）、执行层（管模型能做什么，动作生效前验证）、数据层（管世界最终被改成什么样，由经过人类审查的稳定机制强制执行）。

**Q：为什么上下文层护栏给不出保证？**
→ 处在同一个上下文里的 Agent 很难判断自己是否已被注入——这是结构性上限，所以必须有执行层和数据层。

**Q：执行层护栏的核心机制是什么？**
→ 工具风险评级：按可逆性、权限等级、财务影响为每个工具标注风险等级，高风险操作需额外审查或人工确认。

**Q：参数不同风险不同怎么办（如 delete_file 删普通文件 vs 系统文件）？**
→ 按本次具体调用的参数动态定风险；规则未覆盖的参数组合默认给高风险以保证安全。

**Q：人工干预（Human in the loop）的价值是什么？**
→ 让 Agent 在不损害用户体验的前提下提升实际性能，部署早期尤为重要——识别失败模式、发现边缘情况、建立评估周期。

**Q：用户不在线或响应很慢时 Agent 怎么办？**
→ 高风险默认暂停，低风险降级继续，所有状态存好并最好能回滚。

### Q3：贯穿全书的设计模式有哪些？

**Q：产出与评判如何分离？**
→ 提议者-审核者（Proposer-Reviewer）：两个不共享上下文的角色分别承担，评判方看产物本身（渲染结果、测试输出、调用参数）而非产出方的推理过程；成立前提是自审不可靠。

**Q：信息太多如何喂？**
→ 渐进式披露（Progressive Disclosure）：先给可检索的目录，再按需加载细节。

**Q：状态如何演进才可信赖？**
→ 只增不改（Append-only）：换来可缓存、可重放、可审计。

**Q：如何验证一次修改是安全的？**
→ 边界集 + 保留集：同时在"应当改变的那批样本"和"不应当影响的那批样本"上验证。

**Q：修改如何做到可归因？**
→ 最小 diff + 可回滚：每次修改尽量小、带来源、可单独回滚，出了问题能定位到具体哪一次改动。

## 第 2 章　上下文工程

### Q1：为什么说上下文决定 Agent 的能力上限？

→ 一个中等能力的模型配上精心组织的上下文，往往胜过顶级模型在信息匮乏下的盲目摸索；以 Coding Agent 为例，缺了代码信息、流程规范、环境信息这三类最低信息需求，Agent 写出的代码可能语法正确但架构冲突、直推主分支、本地能跑测试环境即崩。

### Q2：Agent 调用 LLM 的 API 上下文长什么样？

→ 核心逻辑只有一个 while 循环和一个判断：模型返回 tool_calls 就执行工具并把结果追加进 messages 继续循环，没有就输出结果退出——整个过程中 messages 列表只增不减。

### Q3：如何设计对 KV Cache 友好的上下文？

#### Q3.1：KV Cache 的工作原理是什么？

→ 模型每生成一个 token 都要回看前文所有 token 的中间计算结果；KV Cache 把前文的中间结果缓存下来，下一轮只算新增部分。前提是复用的上下文 token 前缀保持不变——从首个不同的 token 起，缓存需要重算。

#### Q3.2：由此得出哪三条核心结论？

→ ① 系统提示词和工具定义一旦确定就不要改（哪怕一个空格都可能破坏缓存）；② 动态信息永远追加到末尾，不修改已有前缀；③ 使用标准 API 格式，不要自行拼接 "USER: ... ASSISTANT: ..." 消息。

#### Q3.3：常见的错误上下文管理模式有哪些？

→ 五种反模式：

- **动态系统提示词**（系统提示词加时间戳）：应把时间信息作为用户消息追加到末尾，或需要时通过工具获取。
- **动态用户配置**（每次请求更新余额等）：破坏缓存，应交给专门的状态管理机制。
- **工具定义动态排序**：改变顺序让缓存从首个变动的工具起全部失效；实验表明保持固定顺序对工具选择能力几乎没有影响。
- **滑动窗口**（只保留最近几条消息）：既破坏前缀一致性，又丢失关键的工具结果——实验中使用滑动窗口的 Agent 常陷入循环，反复执行相同调用。
- **文本格式化**（转为纯文本流）：关键不在缓存，而在于偏离训练时的角色结构格式，导致重复执行、忽略结果、格式解析错误等各种问题。

#### Q3.4：KV Cache 和 Prompt Cache 有什么区别？

→ KV Cache 是模型内部机制（加速单次请求内的 token 生成），Prompt Cache 是推理引擎优化（在多次 API 请求之间复用相同前缀的计算结果）；两者都利用前缀不变性，但作用层级不同。

#### Q3.5：缓存如何反过来约束架构？

→ 当 Prompt Cache 经济效益足够显著时，缓存一致性会反过来主导系统结构：动态元素都往后放、子 Agent 与父 Agent 字节级对齐以命中缓存、工具结果替换字符串首次出现即持久化。

**Q：滑动窗口丢信息与全量保留爆上下文如何两全？**
→ 口诀：前面别乱改，后面只追加，旧内容别丢，放到外面能查。

**Q：ReAct 循环的 KV Cache 读取量为何近似二次方增长？**
→ 上下文只增不减，第 n 轮要读取前 n-1 条消息的缓存，累计为 O(n²)；解决思路是按需携带关键信息、历史过多时压缩（注意压缩后缓存重建）、用子 Agent 隔离。

### Q4：系统提示词该怎么写？

→ 六个优化方向：

- **语气与风格**：大写强调（Never do X）能引起模型注意，但过度使用会稀释效果，保留给真正关键的约束。
- **结构化提示**：用 markdown 标题、XML 标签表达层次与精确语义——模型对结构化输入显著敏感。
- **流程驱动优于规则堆砌**：像优秀的新员工培训手册，提供清晰的 SOP（先干什么、再干什么、怎么收尾）。
- **业务规则细化**：让 Agent 在明确框架内发挥能力。
- **Few-shot 示例**：当期望输出难以用规则精确描述时，直接给出高质量的输入-输出示例。
- **防注入**：来源标记（包裹并标注不可信来源）、指令与数据分离（严格用角色体系传信息）、输入清洗（过滤可疑模式）。

**Q：多人维护系统提示词如何防止"熵增"？**
→ 审核，不让人人乱改，派专人维护。

### Q5：提示词越写越长怎么办？

→ Agent Skills 的渐进式披露机制：按需加载，而非一次性塞满（既浪费 token，又稀释注意力）。

**Q：Skill 在上下文中的位置如何安排？**
→ 标准只规定加载时序而非消息角色：目录必须先于正文可发现，正文在被选中后按需加载。Claude Code 的实现是目录作为运行时上下文消息提供，完整指令在被调用位置作为 user message 注入。

**Q：模型不知道自己不知道，无法触发 Skill 加载怎么办？**
→ 模型可以不知道自己不知道，但系统必须在结构上安排它在关键节点看一眼（如小模型/工具做 skill 检索匹配）。

**Q：加载了 Skill 就等于持续遵从吗？**
→ 不——加载 Skill 不等于持续遵从，长轨迹中义务会一条条静默漏掉。

### Q6：如何让 Agent 感知自己的运行时状态？

→ Agent 状态栏：把任务进度、环境变化、工具调用计数等动态信息整理成结构化摘要，作为 user 角色消息插入上下文末尾（而非修改开头的 system 消息）。

**Q：状态栏包含哪些内容？**
→ 任务规划（TODO 列表放轨迹末尾）、事件侧信道信息（时间、位置、时间间隔）、环境观察摘要（系统时间、工作目录、异常提醒如"该工具已被重复调用 N 次"）。

**Q：状态更新有两种实现，如何取舍？**
→ 实现一"每轮替换"：移除旧状态追加新状态，保证只有一份最新状态，代价是旧位置之后的缓存失效；实现二"持久追加"：缓存友好，代价是陈旧状态积累。状态小、两次更新间消息多、会话长度受控时选持久追加；状态大、更新频繁、轨迹很长时选每轮替换。

**Q：状态栏维护要注意什么？**
→ ① 尽量用代码维护，用 LLM 也要逐条抽取再由代码汇总，绝不让 LLM 一次性批量统计；② 谨慎删除原始上下文。

**Q：状态栏本身出错（计数器 bug）怎么办？**
→ 计数、阈值这类交给代码算，别交给模型"感觉"，且计算组件必须写测试。

### Q7：上下文膨胀了怎么办？

#### Q7.1：为什么注意力机制需要外部辅助？

→ 注意力擅长在已有内容里"查找"，不擅长在一次前向传播里"归纳统计"——上下文学习本质上是检索而非推理。状态栏（代码确定性维护）和压缩（LLM 蒸馏）是同一枚硬币的两面，都在给这台"只有一半"的检索引擎补上缺失的"提炼"。

**Q：状态栏也常由 LLM 生成，这矛盾吗？**
→ 不矛盾，关键在量级：小范围、近期、目标明确的归纳准确率可接受；信息量膨胀到整个长对话历史时，注意力出现"归纳瓶颈"——找得到相关信息，但难以综合成准确的全局结论。

**Q：三者如何对比？**
→ 状态栏（LLM 生成）：面对最近几百~几千 token，提炼"当前做到哪了"，出错成本低；压缩（LLM 蒸馏）：面对整个对话历史上万 token，提炼"过去 50 轮所有关键决策"，出错成本高、易丢细节；纯注意力：无提炼全靠检索，长程召回差。

#### Q7.2：压缩如何与 KV Cache 共存？

→ 压缩发生在两次 API 调用之间，由框架对消息列表预处理：静态前缀永远不动；压缩对象是对话历史中的 tool results，替换位置之后的缓存失效、之前仍有效。这是有意识的权衡——不压缩则上下文超窗任务直接失败。频次上最好接近阈值时批量压缩，而非每轮都压。

#### Q7.3：压缩策略有哪几档？

→ 五档递进：① 无压缩；② 非任务感知压缩（缺语义理解，无法区分相关性）；③ 上下文感知压缩（压缩提示中带 query 和 context，效果好）；④ 带引用的上下文感知（语义压缩有损 + 源链接无损索引，可随时回溯）；⑤ 自适应窗口化（小于 80% 保留原文，超出批量压缩）。生产系统通常组合为分层压缩机制。

**Q：128K 字符压到 2000 字符的极端压缩如何避免不可逆损失？**
→ 核心思路：不要把"压缩"做成"删除"，要做成"索引 + 可回查"。

#### Q7.4：有没有比压缩更釜底抽薪的方案？

→ 隔离优于压缩：子 Agent 上下文隔离——把"大范围搜索"这类产生海量中间内容的任务委派给子 Agent，它在自己的上下文中完成探索，只把几百 token 的结论性摘要回传主上下文。

**Q：思考内容（reasoning）该留该扔？**
→ 行业定位已从"可丢弃的 token 消耗品"（DeepSeek R1 剥离全部历史思考）转向"必须维护的运行时状态"（V4 强制回传全部 reasoning_content）——思考链是 Agent 的草稿纸，写着目标、假设、排除项和下一步。工程上不是"全留"或"全扔"二选一，而是近处保原文、远处压状态。

## 第 3 章　用户记忆和知识库

### Q1：如何理解持久化记忆体系的两个尺度？

→ 用户记忆是针对单个用户的个性化记忆（让 Agent 成为"懂你的助手"，代表框架 Mem0）；知识库是面向所有用户共享的集体知识（让 Agent 成为"领域专家"，代表技术 RAG/embedding）。

### Q2：用户记忆系统如何设计？

#### Q2.1：记忆分几层？

→ 两层：轨迹（单次会话的完整原始记录，按时间追加且不修改——流水账）和长期记忆（跨会话提炼的稳定信息，反复改写合并淘汰——档案）。

#### Q2.2：记忆用什么格式存储？

→ 四种：Simple Notes（最小不可分事实，开销低但丢失关联）、Enhanced Notes（带完整上下文的段落，代价是重复与重写复杂）、Json Cards（类别→子类别→键值对三层嵌套）、Advanced Json Cards（加入来源叙事、主体身份、关系、时间戳——同一条信息在不同场景含义完全不同）。实践标准：关键且少量用 Advanced JSON Cards，大量非关键用 Simple Notes，多数系统混合使用。

#### Q2.3：认知科学如何映射到 Agent 记忆？

→ 工作记忆 = 上下文窗口（含轨迹和从长期记忆激活加载的信息）；情景记忆 = 具体事件（"用户订了下周五去东京的 ANA 航班"）；语义记忆 = 抽象出的稳定知识（"用户是素食者"）；程序记忆 = 行为模式与流程（"先搜直飞 → 确认座位偏好 → 用常旅客号 → 订餐"）。

#### Q2.4：记忆如何压缩与整理？

→ 三层：重要性评分筛选（访问频率、时间衰减、情感强度、信息独特性）→ 聚类（相似记忆分组生成代表性摘要）→ 抽象与泛化（从情景记忆提炼为语义或程序记忆）。

#### Q2.5：工程上如何既保留原始证据又得到可查询状态？

→ 会话结束后先把事实追加到只增日志，再定期从完整日志重建带类型的状态（append-only 原始层 + 派生聚合层 + 提供给模型的记忆工具）。

**Q：用户在不同会话给出矛盾信息（两个住址）怎么办？**
→ 两条记录都保留并标上时间；回答时先判断用户问题（或问用户细节）再取对应时间的记录。

**Q：Mem0 和 Memobase 的思路差异？**
→ Mem0：一次 LLM 调用抽取事实、只做 ADD，查询时融合语义相似度和时间信息排序；Memobase：用户画像（可配置槽位存稳定属性）+ 事件记忆（时间线），采用缓冲批处理摊薄 LLM 调用成本、查询侧只读整理好的画像保证低延迟。

### Q3：RAG 的基础管道如何搭建？

**Q：核心流程是什么？**
→ 文档切块 → embedding 向量化 → 存入向量数据库 → 检索时对查询词 embedding → 相似度检索取回分块 → 注入上下文 → LLM 生成。

**Q：如何提高检索精度？**
→ 三板斧：混合检索（向量语义 + BM25 关键词，取长补短）、重排序（向量库快速召回 Top-50/100，交叉编码模型精排取 Top-3/5）、上下文压缩/精炼（小模型提取关键句子再进 Prompt）。

#### Q3.1：文档如何分块？

→ 四种策略：固定大小切分（简单但截断关联信息）、递归/结构感知切分（按章节段落句子递归，生产默认选择）、语义切分（在嵌入相似度骤降的"语义断崖"处切分，质量高但需额外计算）。块大小与重叠量是典型权衡：块太小语义模糊（"收入增长 3%"——哪家公司？），块太大嵌入稀释、精度下降；常见起点 256-1024 token、重叠 10%-20%。

#### Q3.2：稠密嵌入与稀疏嵌入分别解决什么问题？

→ 稠密嵌入（Word2Vec → GloVe → BERT → Sentence-BERT → BGE-M3）：深度学习把文本映射到向量空间，语义相近则向量距离近，用余弦相似度检索——但可能漏掉关键词。稀疏嵌入（TF-IDF → BM25）：极高维向量、绝大多数维度为零，基于词袋模型做精确关键词匹配——但不理解语义（"猫追狗"和"狗追猫"完全相同）。生产中 ANN 算法（近似最近邻，类跳表 O(log N)）支撑百万级文档的快速查找。

#### Q3.3：检索质量用什么指标衡量？

→ recall@k（前 k 个里有没有相关文档，只看"有没有"）；MRR（第一个相关文档排第几，只看"第一个"）；nDCG（整体排序质量，越多相关文档排得越靠前越好，靠后的折扣越大）。

### Q4：扁平文本检索什么时候不够用？

**Q：判断标准是什么？**
→ 查询主要是"找到包含某信息的文档片段"（如"退款政策是什么"）时混合检索就够；查询需要跨文档综合（"SSE 和 AVX 指令集在架构上有什么区别"）或多层次导航（"从整体架构到具体指令逐步深入"）时，结构化索引才值得投入——代价是索引构建和查询都要更多 LLM 调用。

**Q：扁平检索的两个典型失效案例是什么？**

- **黑猫白猫计数**：100 个案例块（90 黑 10 白），top-k=20 只能看到不完整样本，模型得出错误比例——预先生成统计摘要（"共 100 只：90% 黑、10% 白"）并索引，一次检索即得准确答案。
- **Xfinity 优惠资格边界**：几百条个案工单没有一条写资格范围本身；最近邻偏置（"护士"最接近"医生"的工单）、边界语义缺失（"仅限……其他一律不适用"不存在于任何单条）、完整性信号缺失（模型不知道自己没看全）。解法是离线通读工单库提炼规则卡。

→ 共同结论：把原始案例不加处理地放进知识库远远不够，必须在索引阶段主动提炼、抽象和结构化。

### Q5：结构化索引有哪几条路线？

#### Q5.1：树状层次索引（RAPTOR）适合什么？

→ 自下而上递归抽象：全局摘要 → 聚类摘要 → 具体文本块。查询"SSE 指令集"时从"SIMD 指令集"宏观概念沿树向下钻取到叶子细节——适合"从概念逐步钻进细节"的查询。

#### Q5.2：实体关系图索引（GraphRAG）适合什么？

→ 文档知识建模为实体-关系三元组（主语-关系-宾语，如（北京，是首都，中国））构成的知识图谱。查询"SSE"时定位实体、遍历关系边到"XMM 寄存器"、"浮点运算"——适合"A 和 B 之间是什么关系"的关系性查询。

**Q：知识图谱的固有局限是什么？**
→ 三元组化导致语义降级（"如果下周还下雨就取消海边计划改去博物馆"的条件逻辑和时间依赖全部丢失），且提取准确性依赖 LLM、错误提取导致知识污染。推荐分层互补：完整自然语言保存核心信息 + 结构化元数据做索引检索。

**Q：RAPTOR 和 GraphRAG 如何选？**
→ 前者管抽象层次（跨层穿梭），后者管关系网格（图上漫游）；生产场景组合使用通常比单选效果好。

#### Q5.3：文件系统范式（OpenViking）是什么思路？

→ 把所有上下文（记忆、资源、技能）映射为虚拟文件系统的目录和文件（viking://resources/、user/memories/、agent/skills/），每个条目有唯一 URI；核心是 L0/L1/L2 三层按需加载——L0 摘要约 100 tokens 判断相关性、L1 概览约 2000 tokens 支撑规划决策、L2 全文仅在深入时加载，大部分查询到 L1 即完成。选 Markdown 纯文本而非专用数据库，是为了用户可直接阅读编辑、可 Git 版本控制回滚。

**Q：文件系统范式相比向量数据库 RAG 何时更有优势？**
→ 需要人机共同维护、需要追溯和回滚、Agent 要自己探索而不是一次召回的场景。

### Q6：知识应该如何更新？

→ 双路径：事件触发的增量更新（把知识库当代码库，每次知识变更当一个 Pull Request）+ 周期触发的全量整理（去重去旧合并、回到原始数据核查、冲突解决与场景限定）。

**Q：Reviewer 与 Proposer 同模型且只看上游挑选的片段，会合入什么错误？**
→ 三方面改进：Reviewer 换不同家族的模型（模型独立性）；Reviewer 能自主检索完整知识库和原始证据（证据覆盖）；强制分工——Proposer 只写工作分支，Reviewer 只读证据提交结论，只有合并流程能更新主分支（工具权限）。

### Q7：Agentic RAG 与传统 RAG 的区别是什么？

→ 把 RAG 检索做成一个工具，由模型决策是否检索、检索到什么程度；模型可以分解问题进行多步检索。注意 RAG 的安全边界——防知识库投毒。

**Q：如何解决分块丢失上下文的问题？**
→ 上下文感知检索（Contextual Retrieval）：向量化索引前先用 LLM 为每个文本块生成包含核心上下文的前缀摘要，前缀与原文块拼接后再索引。

**Q：主动服务如何落地？**
→ 双层记忆架构：Advanced JSON Cards 把少量关键事实结构化常驻上下文（全局概览），上下文感知检索按需从海量原始对话取回细节（精确细节）——只靠常驻会丢细节，只靠检索会缺全局视野，两者结合才能主动服务。

## 第 4 章　工具

### Q1：工具分哪几类？

→ 五类：感知工具（获取信息：web_search、knowledge_base_search）、执行工具（改变世界：shell_exec、write_file）、协作工具（与其他 Agent/人协作：spawn_subagent、send_message）、用户沟通工具（向用户传递信息：reply_to_user、send_card）、事件触发工具（外部世界驱动 Agent：set_timer、monitor_shell）。

### Q2：一项能力该用什么形式表达？

**Q：专用工具、通用执行器、Skill 如何选？**
→ 默认取向：通用工具优于专用工具，除非有明确的安全、权限或性能理由。具体看四点：① 安全与权限（需精细授权、审计留痕、不可逆风险 → 专用工具封装）；② 参数复杂度（嵌套对象、多字段联合校验 → 专用 schema 引导，简单参数走 CLI 即可）；③ 变更频率（频繁变化 → Skill，改文本远比改代码部署轻；稳定底层 → 专用工具）；④ 模型能力（强模型用 Skill + 通用执行器表达更多能力，弱模型需要结构化 schema 引导）。

**Q：通用执行器还有什么常被忽视的好处？**
→ 让模型用代码编排工具调用——用代码串联多个工具，而不是一次调一个、把每个中间结果都搬进上下文。

### Q3：工具描述该怎么写？

→ 核心是让 LLM 知道"什么时候用"，而不只是"能做什么"："当需要获取实时信息或查找未知事实时使用" 优于 "搜索相关内容"。要点：边界条件（做不到什么、不接受什么）往往比能力描述更重要；参数描述用具体例子代替抽象规范；返回值结构写清楚（"返回 JSON 数组，含 title/url/snippet"）；为每个工具附 1-5 个真实调用示例。

**Q：Agent 频繁选错工具时先查什么？**
→ 优先检查工具描述而不是怀疑模型能力——大多数选择错误的根因是描述不准确（边界不清、缺少反例、参数含义模糊）。

**Q：参数传递的保真性指什么？**
→ 模型感知到的世界与工具操作的世界之间不能存在系统性偏差——不得在模型不知情的情况下静默修改输入或输出（如把弯引号偷换成直引号，会让模型读取验证时陷入困惑）。

### Q4：工具生态如何构建？

**Q：MCP 是什么？**
→ 客户端-服务器架构的标准化协议：MCP 服务器暴露一组工具，客户端（Agent 框架/IDE）通过标准协议通信；JSON Schema 定义参数；传输层本地用 stdio、远程用 Streamable HTTP；资源与工具分离。

**Q：Skill 如何分发？**
→ 不需要协议——一个 Skill 就是一个装着 SKILL.md 的文件夹，分发机制是注册表（registry）而非协议。

**Q：接入第三方能力的共同风险是什么？**
→ 把一段不受自己控制的文本注入 Agent 上下文，往往还把凭证交到别人手里。对策：接入前审查工具描述、锁定服务器版本、为每个服务器配最小权限凭证。

### Q5：工具太多怎么办？

→ 三层解法，一层比一层"按需"：

- **层次化组织与按需加载**：按信息源性质分类（搜索/读取/解析/查询），不把全部定义一次性塞进上下文；检索式预筛选按语义相似度先筛候选——局限是按初始查询一次性匹配，无法预见多步骤跨领域的工具链需求。
- **主动工具发现**：Agent 执行中意识到能力缺口时主动用自然语言声明需求，系统动态匹配注入；工程上等价于保留少数基础工具 + 一个"工具搜索工具"。KV Cache 友好的做法：新工具 schema 追加到上下文末尾，静态前缀保持稳定，schema 固定在轨迹原位置继续命中缓存。
- **Skills**：不把工具当正式定义注册检索注入，而当成可随手翻阅的参考资料。

**Q：还有别的思路吗？**
→ 参考人类专家：先分专业领域，再按岗位给权限，最后小范围试错。

### Q6：感知工具要注意什么？

→ 搜索类返回要分页：默认只返回前若干条并注明总数和翻页方式，由 Agent 自主决定是否继续，不一次性倾倒；读取类要有 offset/limit 和截断策略，截断时明确标示省略了多少、如何读剩余。多模态感知有三条路径：模型原生多模态、自动提取为文本再处理、把多模态模型封装为工具。

### Q7：执行工具如何平衡能力与安全？

→ 八项机制：输入验证（防 `../` 越界）、权限控制（工作目录限制、命令黑名单、API 配额）、提议者-审核者（不同供应商模型独立审查，两个模型系统提示词一致但关注点差异——提议强调行动导向，审批强调风险控制）、Sidecar 机制（与主思考并行的轻量级安全校验；也用于旁路构造上下文——筛选记忆、摘要长输出，主模型需要时已就绪）、可验证则自动验证、长输出截断与持久化（头尾入上下文，全文存临时文件）、沙盒隔离、可观测性（日志、审计追踪、性能指标、告警）与幂等性/取消语义。

#### Q7.1：沙盒隔离的层级如何递增？

→ ① 进程级（Claude Code/Codex 默认本地执行——但注意实际权限取决于宿主的沙盒与审批策略，如 Codex 的 workspace-write、Claude Code 的只读起始权限）；② 容器（独立文件系统和网络栈，但共享内核，内核漏洞可能逃逸）；③ microVM/虚拟机（Firecracker，独立内核的硬件级隔离，运行完全不可信代码的最强层级）。常见误区：venv 不是沙盒——只隔离包依赖，对文件系统、网络、进程没有任何安全约束。容器和 microVM 还应设 CPU/内存/磁盘/网络上限。

#### Q7.2：幂等性与取消语义如何设计？

→ 核心问题：调用被取消或超时后，副作用到底发生了没有（转账超时可能已转出，盲目重试就重复转账）。幂等性让"执行一次"和"执行多次"对外部世界影响相同，可安全重试：手段一是操作携带唯一标识由服务端去重，手段二是先查询后变更。不可幂等的操作（发邮件、对外转账）用"预检-确认"两段式：先用不同模型家族 + 专用安全提示词做校验，再真正执行；执行失败不盲目重试，把详细错误返回主模型重新规划。

### Q8：协作工具如何设计？

→ 三组原语：启动与取消（spawn_subagent / cancel_subagent——任务失去意义时及时终止避免浪费 token）、消息传递（双向 send_message）、发现（list_agents 列出可用 Agent 及职责与状态——与 MCP 的 tools/list 同一思路）。其上承载四种形态：同步调用、异步调用（任务 ID + 事件通知）、流式协作、多轮交互。再叠加人工介入、超时和降级策略、反馈循环（可归纳的判断进知识库或 Skill，隐式偏好形成后训练数据）。

## 第 5 章　Coding Agent 与通用 Agent

### Q1：通用 Agent 的架构长什么样？

→ 核心是一个 Coding Agent + 文件系统。因为几乎所有高效的内容生成最终都要落到代码上——代码生成是效率最高、成本最低、可复用性最强的能力基座。

### Q2：Coding Agent 如何设计？

#### Q2.1：Coding Agent 配备哪些核心工具？

→ 七个核心工具（感知 + 执行）：Code Interpreter（沙盒执行 Python）、Bash Shell（跑测试、处理特殊格式文件）、读文件、写文件、编辑文件、Glob（按模式匹配文件名）、Grep（按内容模式搜索）。

#### Q2.2：OpenClaw 架构的执行流是什么样的？

→ 以"分析上季度销售数据并生成报告"为例：读记忆（MEMORY.md 发现用户偏好 PDF、数据在 Google Sheets）→ 调工具（搜索 API 用法、代码下载数据）→ 写代码（pandas 聚合、matplotlib 可视化）→ 生成产物（report.pdf、charts/）→ 更新记忆（记录数据源，下次不再问）。文件系统是信息流转的枢纽——记忆从文件读，产物写文件，经验存文件。

#### Q2.3：Coding Agent 的整体流程是什么？

→ 五步：项目文档化（AGENTS.md/CLAUDE.md）→ 任务理解与需求澄清（明确边界和目标）→ 编写设计文档（给用户审查批准后继续）→ 代码实现与测试（测试通过 + 审查通过才算完）→ 文档同步与交付（架构文档同步更新）。

#### Q2.4：为什么 Coding Agent 是成熟度最高的 Agent 类型？

→ 不是因为代码生成模型特别强，而是因为软件工程几十年积累的基础设施天然构成一套强大的 Harness：测试套件提供验收标准，Linter 和类型检查器提供即时自动化验证，Git 提供完美的版本控制和回退能力。

**Q：其 Harness 实践为所有 Agent 系统提供了哪些可迁移原则？**

→ 四条：① 约束优先于指导（能用代码强制的规则就不要用文档建议——Linter 是"做不了"，提示词"请遵循"只是"建议别做"）；② 验证要自动化（人工审查是不可扩展的瓶颈）；③ 反馈越快越好、越结构化越好（错误信息越接近错误发生时刻，纠正效率越高）；④ 回退要可靠（Git 分支、沙盒、快照让错误可逆，Agent 才敢大胆试错）。

**Q：并行工具调用时故障如何传播？**

→ 原则是故障只在同一批并行调用内传播，不上升到父级操作——同时读三个文件，一个找不到只报告这一个失败，不取消另外两个，更不让整个任务中止。

### Q3：故障和错误如何恢复？

**Q：故障按位置分几层？**

→ 四层：API 层（限流 429、超时、连接中断——基础设施噪声，与任务无关）；工具层（幻觉调用、参数畸形、执行异常，最危险的是工具反复返回同一错误而模型不加改变地反复重试）；上下文层（窗口溢出、压缩失败、轨迹结构损坏如工具调用缺配对结果）；控制流层（死循环与死亡螺旋——错误触发的恢复逻辑自身又调用 LLM 再出错）。

**Q：不表现为错误的故障怎么办？**

→ 需要独立的活性监控：空闲看门狗（watchdog timer）——超过设定时间没有新输出就判定卡死，主动杀死挂起的流并触发重试。

**Q：如何检测无进展循环？**

→ 两种模式：重复调用指纹（对"工具名 + 参数"计算指纹，相同指纹反复出现即明确信号）；连续失败计数（每条恢复路径独立计数器，为熔断提供依据）。

**Q：恢复方案的优先级是什么？**

→ 三级递进：静默重试（可重试错误的默认动作）→ 降级与接续（重试无效时改变请求本身再试）→ 暴露给用户（所有自动手段用尽后才呈现错误，并附上已尝试过的恢复动作）。

### Q4：Coding Agent 有哪些实现技巧？

→ 并行工具调用、流式执行与级联中止；上下文精细化管理（带行号精细化读取，不全量读文件）；环境信息动态注入（工作目录、git 分支、最近提交）；命令执行环境状态持久化（专用持久化终端会话）；即时语法反馈（写入一完成就自动跑 linter，结果作为工具返回值的一部分——好比 IDE 报错）。

**Q：搜索工具为什么刻意不建嵌入索引？**

→ 以 Claude Code 为代表的终端型 Agent 纯靠 agentic 的 grep + glob 现场检索——既不必维护随代码演化而不断陈旧的索引，也省掉一整套索引基础设施。

**Q：文件编辑工具有哪几种设计？**

→ 五种：差异描述 + Apply Model（模型生成 git diff 式变更描述，框架应用）；old string → new string 字符串查找替换；行号定位（删除第 X 到 Y 行插入新内容）；类 Vim 编辑命令（复制剪切粘贴，重组代码高效）；字符串首尾匹配（只给开头和结尾几行，中间可省略，框架匹配首尾定位替换区域）。

### Q5：Coding Agent 的安全如何设计？

**Q：风险的本质是什么？**

→ Simon Willison 的"致命三要素"：访问私有数据（能读用户文件和密码管理器）+ 暴露于不受信任内容（邮件网页可能带恶意载荷）+ 具备外部通信能力（能发邮件执行命令）——三者同时满足即可能造成不可逆损失。

**Q：隔离兜底怎么做？**

→ 代码执行沙盒工程选型：网络出口控制、文件系统隔离范围、资源限额与超时（CPU/内存/磁盘配额，防御死循环、fork 炸弹和无限写盘）。

**Q：多方委托下 Agent 为谁效忠？**

→ 对主人绝对忠诚，对外部交互方保持审慎。

### Q6：代码为什么是通用 Agent 的元能力？

→ 七个角色：思考工具（纯思考算错数，代码计算更精确）；业务规则约束（自然语言边界模糊有二义性，代码规则明确）；多媒体生成驱动（PPT、视频、3D 与工业零件）；系统适配器（无现成 SDK 时当场读文档生成适配代码）；生成式 UI（交付 HTML 表单收集信息澄清意图）；生成 SQL 和软件；创造代码——Agent 自举与自我进化。

**Q：安全性和代码能力如何平衡？**

→ 能力按需求来给，权限按次给，用完就收回。

**Q：如何防止 Agent 自举的代际退化？**

→ 保留一份人类审核过的高质量基线，没过基线不上线。

**Q：Agent 生成代码、系统执行代码的分工如何保证安全？**

→ 模型负责写，执行环境负责拦截，安全性问题交给 Harness，别太相信模型的决策。

## 第 6 章　交互：观察与动作空间的扩展

### Q1：为什么需要扩展交互？

→ 前面的 Agent 与世界是轮流交互的——它思考时世界被默认静止，而现实不是。两个扩展维度：模态决定观察和动作的形式（只读文本还是能听能看能驱动关节）；触发时机决定节奏（观察是主动取还是世界推来；动作是回合内做完还是可跨回合、被打断、被抢占）。

**Q：四个时间尺度上交互如何变化？**

→ 秒—天（异步事件驱动：被外部事件唤醒，动作跨回合）；10ms—1s（语音：边说边听、边想边说、可被打断）；亚秒—秒（Computer Use：屏幕两帧间持续变化，动作后必须重新确认现实）；毫秒（机器人：传感器连续回流，动作分块、一次规划一小段可被抢占）。

### Q2：异步与事件驱动如何设计？

**Q：OpenClaw 提供哪三种事件驱动机制？**

→ Hooks（响应生命周期事件，类似 GitHub Actions 触发器）、Cron（按表达式周期执行）、Heartbeat（每 N 分钟唤醒检查）。短板：对内置渠道之外的第三方事件源（新邮件、API 回调）缺乏即时接入通道，只能等下一个周期。

**Q：事件处理有哪三种策略？**

→ 队列式（等到下一个自然安全点，用于常规事件）、取消式（主动提前制造安全点，用于紧急事件）、并行式（另起循环不等主循环，用于独立轻量查询）。

**Q：不支持原生异步的模型如何兼容？**

→ 运行时安排事件接入顺序：为未完成的工具调用生成占位符 tool result（保证轨迹格式合法），把用户新消息追加到轨迹重新调用 LLM，原结果到达后作为新事件追加，Agent 继续原任务。

**Q：模型原生异步需要什么能力？**

→ GPT-6 Astra 已支持异步工具调用与回合中途引导（Mid-turn steering）。可靠性还要检查三件事：结果归属与未完成状态（延迟结果归入正确任务、缺席时不编造）；任务恢复与动作控制（区分修改计划与停止执行）；多条更新的综合使用（不只记住最后一条消息）。

### Q3：语音交互如何设计？

**Q：语音的价值是什么？**

→ 不只是文字换声音：说话速度约为打字的四倍且不占双手与视线，天然适合持续工作、随时被打断的输入输出回路。

**Q：三种交互范式如何对比？**

→ 级联（VAD → ASR → LLM → TTS：模块清晰易调试，但延迟累积、副语言信息丢失）；端到端 Omni（原生音频出入，延迟低、保留语气情绪，但仍是轮次制）；全双工（持续听说决策，支持重叠说话与自然打断，训练控制评估最复杂）。当前生产环境最广泛的仍是级联——每步有文本中间态，可定位问题，对客服金融医疗政务是硬需求；流式化后端到端能压到 600-800ms，接近人类对话容忍阈值（约 700ms）。

**Q：串行级联的三个问题及流式优化？**

→ 三问题：延迟累积（必须等静音确认说完）、信息丢失（二值信号表达不了犹豫情绪）、上下文被切断（专有名词分片出错）。流式优化：ASR 边听边转、LLM 推测执行（最终文本与临时一致则不重调，否则取消重来）、LLM 分段输出（第一段可播报即交 TTS）、TTS 增量合成。

**Q：实时交互与深度思考如何兼得？**

→ 三个方案：快思考回应 + 慢思考回答（缺陷：两者可能矛盾）；快思考交互 + 慢思考提醒（后台通过状态栏提供建议，前台维持话头，更稳定）；端到端统一。快慢分离的工程优势：直接承接慢模型的迭代红利。

**Q：如何让语音合成更像人？**

→ 传统 TTS 零停顿反而暴露机器身份——停顿、填充词、偶尔重复是人类表达不确定性的信号。让主 LLM 输出控制标记（THINKING、EMO:happy、SPEED:0.8x），由 TTS 映射为停顿、韵律、语速或笑声叹气。

### Q4：Computer Use 如何设计？

**Q：核心循环是什么？**

→ 感知-思考-行动循环：截屏 → 多模态模型接收截图和指令，输出思考和一个具体动作 → 执行层执行（移动鼠标、点击、输入）→ 等界面响应再截屏，进入下一轮。

**Q：视觉定位（Grounding）有哪几条路线？**

→ 两大思路：选择题（先把界面元素标注编号，模型从中选一个）与纯坐标预测（直接看截图报坐标，理解高度依赖训练分辨率）。选择题又有两种实现：纯视觉标注（Set-of-Mark，分割模型切候选区域）与结构化元素索引（DOM/Accessibility Tree，经 CDP 获取）。选择逻辑：结构化信息可得时优先 DOM 索引（最精确稳定）；不可得时（Photoshop、Canvas/WebGL、游戏）用 SoM（对通用模型友好）或坐标预测（对专门训练过的模型直接）。标注不完整时回退到坐标预测。

### Q5：机器人操作如何分层？

**Q：不同时间尺度如何分层？**

→ 五层：任务目标（分钟级）→ 长程规划（秒到分钟）→ 基本技能（pick/place，约 1-3 秒）→ VLA 技能策略（约 1-10 Hz 推理）→ 底层控制与安全层（50-1000 Hz，限速与急停）。

**Q：VLA 的局限是什么？**

→ 四点：训练数据有限（演示远少于互联网文本，见过"杯子"不等于见过各种摩擦条件下的杯子）；只学会模仿不一定懂后果（行为克隆不回答"动作会造成什么结果"）；机器人各不相同（自由度、坐标系、夹爪、延迟不同，动作难迁移）；观察可能过时（动作执行中物体被移动遮挡）。VLA 回答"现在做什么"，还需要世界模型——"动作结果预测器"——判断"做了之后会发生什么"。

## 第 7 章　Agent 的评估

### Q1：评估体系分哪四个环节？

→ 什么算成功（指标）、任务从何而来（数据集）、由谁验证（验证器）、分数如何转化为决策（选型）。

### Q2：成功的定义用什么指标？

→ Pass@k（运行 k 次至少一次通过，看能力上限——能否做到）与 Pass^k（连续 k 次全过且无一票否决项，看业务可靠性——能否每次稳定做到）。单次成功率 60% 的 Agent：k=3 约 94%、k=5 约 99%，k 取到边际收益趋平的位置，要结合重试成本和副作用。

### Q3：评估环境有哪五个要素？

→ 数据集（Dataset）、环境状态（必须可重复）、工具接口（可给 Agent 侧也可给模拟用户侧）、评分标准（Rubric）、执行协议（交互顺序与终止条件）。

**Q：主流基准各自如何设计？**

→ τ²-bench（客服交互，用户模拟器 + 业务数据库）；SWE-bench Verified（GitHub 真实 issue，FAIL_TO_PASS/PASS_TO_PASS 双重验证）；AndroidWorld（参数化模板 + UI 状态断言）；OSWorld（真实虚拟机 + 134 个独立评估函数）；Terminal-Bench（Docker 容器 + 文件系统检查）；GAIA（开放互联网 + 精确字符串匹配）。

**Q：评估数据集从哪来？**

→ 三个来源：公开基准、自建业务集、生产轨迹回流（直接源自线上用户问题，上线后慢慢成为主体）。

### Q4：开放式任务如何自动评估？

→ LLM-as-a-Judge：按专家定义的 Rubric 评判，在自动化规模和人类专业判断之间取得平衡。风险：模型可能系统性给某种风格打高分——检测方法是专门建一个数据集比较人工评与模型评。

**Q：评估结果如何驱动修复？**

→ 失败归因（failure attribution）：从整条轨迹定位首个错误——标出错误类别、首次不可接受行为的步骤、对应工具调用，附可复核证据。再构造两层回归任务：端到端回归（验证改动没破坏完整工作流）+ 轨迹前缀回归（截取首个错误之前的状态，只验证那个决策边界是否修好）。

### Q5：模型选型看哪些指标？

→ 推理两阶段：Prefill（一次性读入上下文，决定 TTFT 首字延迟）与 Decode（逐 token 生成，决定出字速度和思考时长——50 tokens/s 生成 2000 思考 token 光思考就 40 秒）。指标：输入/输出吞吐量、TTFT、思考延迟（思考长度与效果不一定正相关，要实测）、p95 尾部延迟（比均值更能反映真实体验）。再加成本、速率限制与可靠性、预算—能力曲线。

### Q6：可观测性如何建设？

→ 数据基础是追踪（Trace），沿用分布式系统的 span 树模型：一次任务一条 trace，每个 LLM 调用/工具调用/检索是一个 span（输入输出、起止时间、token、错误），父子关系构成执行树。标准化协议用 OpenTelemetry；平台代表 LangSmith、Langfuse、Arize Phoenix，整合可观测性、评估、优化为闭环。价值：问题诊断（回放全过程）、持续优化（哪个工具成功率最低）、成本管理（识别异常高成本案例）、后训练数据基础。

### Q7：外部评估之外还需要什么？

→ 内建持续自我评估：消融实验（特性是真改善还是感觉有用）、AB 测试、特性开关（Feature Flag，远程控制开关无需重部署）、提示词敏感性评估。

## 第 8 章　模型后训练

### Q1：模型能力开发分哪四个环节？

→ 预训练（海量文本预测下一个词，学会语言规律、世界知识、基本推理——"通识教育"）→ Mid-training（在目标语言/领域/能力语料上继续语言建模，领域自适应——"研修专业教材"）→ SFT（标注的输入输出对，学指令遵循、格式、风格——"老师示范答题"）→ RL（反复尝试按奖惩改进——"自己下场做题按得分复盘"）。

**Q：两条主线结论是什么？**

→ ① SFT 更容易记住示范，RL 表现出更好的泛化；② 数据和环境比算法更重要——真正决定成败的是 Mid-training 语料补没补齐底座、示范数据有没有建立行为协议、仿真环境与奖励能不能提供可靠试错反馈，很多场景前两类数据质量到位甚至不需要 RL。

**Q：四阶段在数学上是什么关系？**

→ SFT 和预训练是同一个任务（预测下一个词、最小化同一损失），差别只在数据（人工示范 vs 原始互联网文本）和损失计算位置（只在回答上算损失，问题部分不回传梯度）。RL 用奖励评估模型自己生成的回答，擅长把已有但概率较低的成功行为推高，不擅长从全零奖励中凭空创造模型从未学过的能力。

### Q2：经典 RL 与 LLM Agent 有何不同？

→ RL 核心：根据当前情境选择动作以最大化累积奖励。五要素：动作空间、策略、奖励信号、价值函数、环境模型；数学框架是 MDP（马尔可夫决策过程），核心算法之一是 Q-learning——贝尔曼方程的递归关系：动作真实价值 = 即时奖励 + 下一状态的最大未来价值。

**Q：LLM 的动作空间有何本质不同？**

→ 传统 RL 动作空间有限（移动、攻击、拾取）；LLM 把思考 token 作为特殊动作纳入策略输出空间——不直接改变环境、不立即获得奖励，但能在 token 成本和上下文上限内表达多种计算路径。这种变长组合式动作搜索空间大得多，很难没有先验知识时从零学习。

### Q3：Mid-training 解决什么缺口？

→ 两类：知识缺口（通用预训练没覆盖目标语言、金融/医疗/法律领域、企业文档——连概念术语都不能理解）与基础能力缺口（长上下文、代码模式、数学推导——足够多次采样下也几乎得不到正确解）。数据构造：从失败分布反推、构造高密度目标语料、按能力配比、每阶段"双重回放"、多维门禁决定何时停止。

### Q4：SFT 数据从哪来？

→ 三条路：人工专家示范（质量天花板最高但贵且慢，适合定义格式风格的种子数据）、教师模型生成（合成数据，强模型批量产出过滤后蒸馏）、拒绝采样（自己采样多条候选，验证器筛出正确的反过来训练自己）。

**Q：Mid-training / SFT / RL 如何选择？**

→ 按观察到的现象：概念语言基础操作不会、pass@k 仍接近 0 → Mid-training（动态事实用 RAG）；偶尔做对但格式、schema、流程不稳定 → SFT 或约束解码；已有非零成功率和可靠奖励但好策略概率低 → RL；只有少量稳定示范无环境 → SFT/RFT/离线偏好优化，先建基线再判断是否值得建 RL 环境。

### Q5：后训练有哪些常见陷阱？

→ 十一个：用 SFT 硬塞知识库（稳定知识走 Mid-training，动态事实走 RAG）；格式未稳定就上 RL（解析失败让训练信号稀疏失真）；把标称窗口当有效窗口（128K 输入不等于 128K 上仍会检索推理，用"能力 × 长度"矩阵检查退化）；pass@k 近零仍直接上 RL（全失败 rollout 没有正向轨迹，组内优势消失）；奖励函数设计不当导致奖励黑客（评估最终目标而非中间指标）；忽视仿真保真度（仿真过于简化，策略到真实场景完全失效）；过度训练导致泛化下降（三者都需要独立保留集和早停）；价值函数崩溃与探索不足；训练—推理数值失配（监控 log prob 差异、近似 KL、策略 staleness）；低估 RL 计算成本（可能是 SFT 的 10-100 倍）；训练数据质量低下（垃圾进垃圾出，RL 还会朝错误方向放大）。

**Q：核心原则是什么？**

→ 投入大规模资源前先用小规模实验验证关键假设——小批语料查遗忘曲线、少量 SFT 查格式稳定性、小批 rollout 查 pass@k 和数值一致性。快速失败比大规模失败更可接受。

**Q：评估集用于训练是否违反训练测试分离？**

→ 从评估集中切出一小部分"金丝雀集"，绝不用于训练，只用来监测真实泛化。

## 第 9 章　Agent 的持续进化

### Q1：为什么部署后还需要持续进化？

→ Agent 能零样本解复杂任务却会重复犯错；部署之后参数不会自动更新；存会话轨迹不等于学习，构建记忆保存经历不等于从经历中学习。应建立外围持续进化闭环：记录证据、验证过程、归纳共性、经回归与安全检查后更新知识、指令、程序甚至模型参数。

### Q2：持续进化有哪四种更新方式？

→ 四种载体，各有边界：经验知识库（事实、经验规律、例外与来源——更新快、可追溯，但依赖检索和正确应用）；Prompt 与 Skill（需要理解语境的判断原则——可解释、范围可控，但容易膨胀冲突被忽略）；程序与 Harness（可确定解析、可执行验证、高风险硬约束——可测试、稳定、成本低，但开发维护贵）；模型参数（高维感知、生成风格、隐式策略——泛化强、推理开销低，但更新回归成本高）。

**Q：同一能力如何拆到多个载体？**

→ 事实进入知识库，解释例外的原则进入 Skill，不可绕过的权限由程序门控，高维识别能力进入参数。

### Q3：生产系统如何构建进化闭环？

→ 双循环结构：在线执行循环只完成任务并记录证据，不直接改写正式 Agent；离线进化循环聚合轨迹、诊断根因、生成更新提案，通过验证门槛后发布新版本。两者通过版本化的经验库和评估集连接。

**Q：满意度上升但违规率也上升，为什么不能拿满意度当单一学习信号？**

→ 违规可能付出很高成本，不能拿违规换好评——要设计护栏指标。

**Q：同一个问题该改 Prompt、Harness 还是参数？**

→ 依据危害程度递进：先用 Harness 防危害，再用 RAG 降发生率，最后才考虑模型参数训练。

**Q：Agent 能改工具和验证器，如何防止它改批准自身更新的可信根？**

→ Agent 只能改被评估对象，不能改评估器。

**Q：医疗客服的协同进化方案？**

→ 知识库管客观事实，Skill 管流程，参数管语气风格，代码管硬约束。

## 第 10 章　多 Agent 协作

### Q1：多 Agent 协作如何分类？

→ 维度一（上下文是否共享）：共享意味着后续 Agent 继承前一个的完整轨迹——切换系统提示词和工具集就成了新 Agent 但保留全部记忆；不共享则各维护独立上下文，通信走三条路——工具调用参数（下游封装成工具，适合类型确定结构清晰）、共享文件系统（适合产物大需持久化）、消息总线（专门中转站按订阅转发）。维度二（协作拓扑）：对等协作、管理者模式、去中心化模式。

**Q：这个分类的理论根基是什么？**

→ 操作系统 IPC 的两大范式——共享内存与消息传递。

### Q2：多 Agent 何时真正优于单 Agent？

→ 核心判断只有一条：协作过程中是否引入了单个 Agent 在生成时无法获得的新信息。同一模型自我审查（重新读自己的输出）——不引入新信息，通常无效甚至有害；不同 Agent 辩论同一段文本——等计算量下与单 Agent 持平；审核者用测试执行结果审代码（执行反馈）、看渲染截图审前端（视觉反馈）、用外部工具验证事实（工具反馈）——引入新信息，显著提升。

**Q：增加步骤预算就能提升性能吗？**

→ 不能——标准 Agent 缺乏"预算意识"，300 步预算仍执行浅层搜索很快饱和。需要显式的预算感知机制：前期广泛探索、后期聚焦最有希望的方向（Google 2025 Budget-Aware Tool-Use）；BAVT 进一步做步骤级价值评估，按剩余预算调整探索与利用的权重。

### Q3：共享上下文时，角色转换用 transfer_to_agent 还是 Skill？

→ transfer_to_agent：替换 system prompt 和工具集——约束能力强（越界工具 schema 层不可见），但每次切换改变请求前缀、缓存无法复用。Skill：固定 system prompt 中的目录、按需把 SKILL.md 追加到轨迹——静态前缀不变、缓存可复用，但约束弱（行为指令，硬权限仍需 Harness 门）。选择标准：角色差异主要是知识、流程、写作风格 → Skill；涉及权限、工具隔离、合规边界或需运行时强制禁止动作 → 独立 Agent / transfer_to_agent + Harness 代码限制。

### Q4：不共享上下文的系统与操作系统如何对应？

→ 程序 = 静态前缀，进程内存 = 轨迹，CPU = LLM，内核 = Agent 运行时，系统调用 = 工具调用，fork = spawn_subagent，kill = cancel_subagent，ps = list_agents，退出码与 wait() = 子 Agent 返回的结构化摘要，共享内存/消息传递 = 共享文件系统/消息。

**Q：多 Agent 文件系统分哪四类区域？**

→ Agent 专属工作区（Scratchpad，独享私有目录）、多 Agent 共享空间（共同读写、用户可见）、外部挂载资源（用户授权的第三方信息源，有权限约束主要读取）、系统内置资源（预置只读共享，如 skills）。

**Q：Agent 间的通信与控制有哪四件事？**

→ ① 消息传递：点对点（拓扑固定、数量少）→ Agent 多了连接数平方增长且要求同时在线 → 消息总线（发布订阅解耦）；② 状态查询：消息传递（不用等立马回）或共享文件（轨迹持久化最彻底 / 约定 progress.md 进度文件轻量）；③ 执行终止：优雅终止首选（terminate 信号、安全点清理资源、ack 后退出），强制终止兜底；④ 资源与调度：启动时设步数/token 预算超限即止，困难任务给强模型、机械任务给低成本模型。

**Q：对等协作的关键是什么？**

→ 2-3 个平等 Agent 多轮迭代互评。陷阱：模型、上下文、脚手架高度相似时会做出相同选择，局部错误演变为系统性故障——要主动区分模型、上下文、工具、可见证据或职责，先独立判断再汇总。最经典用途：解决"过早终止"（偷懒式假完成、过早放弃、假成功——根因在验证器不在模型）——用提议者-审核者范式。另有辩论模式（效果有争议）、头脑风暴（前沿）、专家小组。

**Q：管理者模式的关键发现是什么？**

→ Manager 像项目经理：理解任务、拆解、分配、跟踪、处理异常、整合结果。Plan-and-Act 论文的实证：Planner-Executor 架构中弱规划者是整个系统最关键的瓶颈——规划质量足够高时，简单 Executor 也能取得好结果。

**Q：去中心化模式的代表是什么？**

→ MetaGPT：把人类软件公司的 SOP 编码进多 Agent 系统，角色像流水线工种产出标准化交付物，交付物天然构成通信接口。有效"移交包"三部分：任务描述（含验收标准）、已确认的事实与约束、结构化产物引用（文件路径而非内容，按需读取）。通信机制贡献：共享消息池 + 按角色订阅——发布者不需知道消费者，新增角色只需声明订阅，换 PM 模型只要 PRD 符合规范其他角色无需修改。

**Q：跨组织协作用什么协议？**

→ A2A（Google 2025 发布，后捐赠 Linux 基金会）三要素：Agent Card（能力元数据"名片"，解决跨组织发现）、任务生命周期管理（Task 状态机：已提交/进行中/需要输入/已完成/失败，原生支持长任务和流式进度）、不透明协作（只交换任务与产物，不暴露提示词、思考过程和工具实现——跨组织必要的安全属性）。

### Q5：多 Agent 协作有哪些失败模式？

→ 三大类归因：系统设计缺陷（接口不清、职责重叠、工具配置错误）、Agent 间对齐失败（目标理解不一致、信息被误解、操作逻辑矛盾）、任务验证缺失（声称完成但结果不符）。

**Q：六种具体失败模式是什么？**

→ ① 共享文件并发冲突：文件级（后写覆盖先写）与语义级（A 重编全书图片编号、B 同时改章节引用旧编号——文件层面无冲突但结果错误）——解法乐观锁/CAS；② 错误的级联放大：像传话游戏越传越走样——解法交叉验证，让某个 Agent 以独立视角只看原始证据和最终结论是否一致，不看前序思考过程；③ 同质趋同：很多 Agent 做大量重复的事；④ 互相扯皮：后端怪产品、产品怪后端，卡住；⑤ 循环失控：停不下来，失控 Agent 生成数千个子 Agent 浪费 token；⑥ 理解债与认知投降：模型写得越好你越不想看代码，最终失去对项目的掌控。

### Q6：Agent 社会涌现什么？

→ 三类涌现：社交涌现（斯坦福 AI 小镇 25 个 Agent 自组织社交；Agentopia 时间尺度拉长到 10 年；Moltbook 规模推到 150 万——跨过临界点就产生无法预先设计的集体行为）；经济涌现（Vending-Bench Arena 市场竞争经营；Pinchwork、RentAHuman 经济交易市场）；策略博弈（狼人杀实验考验信息不对称下的推理、欺骗与社交操控）。

**Q：一个成功、全员停止的级联终止如何设计？**

→ Manager 维护任务状态表，收到第一个成功信号后立即广播终止并加锁，后续成功拿不到锁也无法改动。
